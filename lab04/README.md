# Лабораторная работа
## Использование паттерна проектирования Separated Interface

---

## Описание предметной области

В работе реализуется система отправки уведомлений через различные каналы связи.  
Пользователь через графический интерфейс выбирает канал и вводит текст сообщения. Система должна поддерживать:

- отправку уведомлений через Telegram, электронную почту и консоль;
- добавление новых каналов без изменения клиентского кода;
- независимость клиентской логики от конкретных реализаций отправки;
- единую точку создания объектов-отправителей.

Каждый канал имеет собственную логику доставки (HTTP-запрос, SMTP, вывод в консоль), что делает прямую зависимость клиента от реализаций нежелательной.

---

## Решение

Для разделения клиентского кода и конкретных реализаций был применён структурный паттерн **Отделённый интерфейс (Separated Interface)**.  
Созданы следующие участники паттерна:

- `INotification` (пакет `interfaces`) — отделённый интерфейс с единственным методом `send(String message)`; живёт в изолированном пакете, не зависящем ни от клиента, ни от реализаций;
- `ConsoleNotification`, `EmailNotification`, `TelegramNotification` (пакет `implementations`) — конкретные реализации интерфейса, каждая со своей логикой доставки;
- `Notifier` (пакет `client`) — клиентский класс; принимает `INotification` и вызывает `send()`, не зная ничего о конкретном канале;
- `NotificationFactory` (пакет `factory`) — единственное место, где создаются конкретные объекты; изолирует знание о реализациях от остального кода;
- `App` — точка входа с графическим интерфейсом (Swing); запрашивает объект у фабрики и передаёт его клиенту.

Клиентская часть взаимодействует с `INotification` через `Notifier`, не обращаясь к конкретным классам напрямую — вся зависимость от реализаций сосредоточена в `NotificationFactory`.

## Сравнение реализации с паттерном и без паттерна

### Реализация с использованием Separated Interface

- интерфейс `INotification` объявлен в отдельном пакете `interfaces`, изолированно от клиента и реализаций;
- `Notifier` зависит только от `INotification`, не импортируя ни один конкретный класс;
- `NotificationFactory` — единственное место, где упоминаются конкретные реализации;
- добавление нового канала (например, SMS) требует только создания нового класса и одной строки в фабрике;
- соблюдаются принципы инкапсуляции и слабой связанности.

Структурно:
- App → NotificationFactory.create(type) → INotification
- App → Notifier.notify(sender, message)
- Notifier → INotification.send(message)

### Реализация без использования Separated Interface

- `App` или `Notifier` напрямую создают объекты: `new TelegramNotification()`, `new EmailNotification()` и т.д.;
- клиентский код импортирует все конкретные классы и зависит от каждого из них;
- при добавлении нового канала необходимо вносить правки в клиентский код;
- нарушается принцип открытости/закрытости, растёт связанность компонентов;
- сложнее тестировать: нельзя подменить реализацию без изменения клиента.

Структурно:
- App → new TelegramNotification()
- App → new EmailNotification()
- App → new ConsoleNotification()
- App → sender.send(message)

## Вывод

Использование паттерна Separated Interface позволило:

- отделить объявление контракта (`INotification`) от его реализации — клиент зависит только от интерфейса;
- сосредоточить знание о конкретных классах в одном месте (`NotificationFactory`), не распространяя его по всей программе;
- упростить добавление новых каналов уведомлений без изменения клиентского кода;
- облегчить тестирование: в `Notifier` можно передать любую тестовую реализацию `INotification`.

В результате система уведомлений стала модульной, слабосвязанной и легко расширяемой.
